# QuickWeds app audit — September 10, 2026

Landing page and feature marketing pages excluded. Assessment of the local checkout, read-only production Supabase metadata and aggregate counts, and local Chromium checks. No application fixes, production mutations, emails, purchases, or account creation were performed. Findings below distinguish observed defects from recommendations and unverified integration risks.

## Local remediation update

The first corrective pass was deployed to production on September 10, 2026. It protects public wedding data and paid entitlements, routes analytics through the server, lets imported pending guests respond securely, enforces RSVP deadlines and invitation party sizes, fixes builder drafts and media retention, corrects budget double counting, removes duplicate FAQ sections, and fixes the Glitch template lint errors. A clean production build passes, ESLint has no errors, and the template suite passes all five tests across 25 templates at four viewport sizes. Post-deploy checks confirmed the public serializer excludes private fields, a real public wedding renders without horizontal overflow, missing weddings return 404, and unauthenticated builder access redirects to login.

## Recommendation

QuickWeds already has enough functionality to deliver meaningful value: invitations, RSVP, planning, seating, check-in, entourage proposals, photo sharing, and supplier discovery. Prioritize reliable publishing and guest responses, then make the wedding-day workflow your differentiator. More templates alone will not resolve the current privacy, persistence, and RSVP problems.

## Fix first: privacy and authorization

**P0 — Private wedding data is readable through the production database API.** Production `weddings` policies include anonymous/public SELECT with `USING (true)`. Anonymous column privileges include `couple_email`, `user_id`, `wedding_party`, `payment_status`, and `stripe_payment_intent_id`. This confirms a broader exposure than the intended public invitation. A server-side public-field allowlist does not close direct database access. Broad policies combine with owner policies; an owner policy does not override a permissive public one.

Fix: inventory direct browser reads, route public requests through a minimal public projection, revoke private-column/table access for anonymous users, and remove broad authenticated reads of private records. Preserve intentionally public invitation content. Verify with anonymous, unrelated-user, owner, partner, coordinator, and admin access tests. Do not blindly revoke all reads without migrating callers such as analytics and slug checks. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

**P0 — Users can grant themselves paid access through direct database writes.** Production grants permit authenticated INSERT/UPDATE of `user_app_profiles.is_pro/payment_status` and `weddings.is_premium/payment_status`. Ownership policies permit users to update their own rows, and the trigger inventory returned no noninternal triggers on either table. Application checks then trust these fields (`src/lib/planner-limits.ts:73`). This is confirmed from grants, policies, and code; no exploit mutation was attempted.

Fix: make payment/entitlement columns server-write-only, protect both INSERT and UPDATE, and derive all feature decisions from one entitlement service. Preserve profile editing using explicit allowed columns or an API. Add a payment-event ledger and reconciliation. Test a direct database write using a disposable staging account, not merely whether an upgrade button is hidden.

**P1 — Public wedding serialization includes private entourage metadata.** `src/lib/public-wedding.ts`, `normalizeWeddingParty`, retains email, proposal message, and proposal template metadata. The public page/API receives this even when UI does not display it. Remove nonpublic fields from the public nested schema; keep name/role/bio/photo only as intended. Invalidate both Redis and Next caches after remediation.

**P1 — Deletion has incomplete cleanup and cache handling.** `src/app/api/account/delete/route.ts` logs and continues after several cleanup errors, can fall back to `deleted_at` plus `user_id = null`, and does not invalidate public wedding caches or remove stored media. Production's `auth_manage_weddings` policy also allows management of rows with null owners. This creates a problematic combination if a deletion falls back. Actual affected rows were not inspected.

Fix: remove the null-owner management allowance, use a resumable deletion job with explicit completion/error states, revoke sessions, invalidate public caches, and track storage/provider cleanup. Test failed substeps and deleted-page behavior. Define and document retention instead of returning success while silently skipping required cleanup.

**Production advisory cleanup, separate from confirmed exposures.** The live advisor reported six mutable function search paths, six anonymous-callable security-definer functions, and leaked-password protection disabled. Review each function's purpose before changing it; public domain lookup is intentionally callable, and a trigger function's execute grant alone does not prove an exploitable RPC. GraphQL schema visibility warnings are not evidence that protected rows are public. RLS-enabled/no-policy tables may intentionally be server-only.

[Function search-path remediation](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable), [security-definer review](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable), [password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).

## Builder, templates, and style

**P1 — Photo editing does not preserve the gallery correctly.** In `BuilderForm.tsx:1319`, new invitation uploads replace the prior array instead of merging. Gallery and reception uploads have the same replacement behavior. Gallery save falls back to `formData.gallery_images`, whereas loaded gallery URLs are stored in `previews.galleryImages`; removing an existing gallery photo can therefore fail to persist. Removal also uses one index for a previews array containing old+new images and a files array containing only new images.

Fix: one ordered media model with stable IDs, persisted URLs, and optional local files. On save, replace only local file entries with uploaded URLs. Test adding one photo to three existing photos, removing an old photo, removing a new photo, reordering, retry after failed upload, and reload. Couple assets are emotionally important; this is a retention issue.

**P1 — Ordinary draft editing is not recoverable.** The ten-step builder holds state in memory and saves on final submission. `pending_wedding_data` only handles the login branch; preview session storage is not restored as a normal builder draft. No ordinary autosave or navigation-loss guard was found. Refreshing or closing during a lengthy setup can lose work, especially files.

Fix: debounced draft autosave, explicit Saving/Saved/Retry states, recoverable uploads, resume on another device, and separate draft from public publication. Preserve the existing live preview and health checks.

**P1 — Duplicate FAQ composition is reproduced in Chromium.** Classic renders its FAQ (`ClassicTemplate.tsx:151`), and `WeddingPageClient.tsx:130` appends another. Multiple other templates also render FAQ. Pick one section owner and make each section ID unique. Do not hide the failing test with `.first()`.

**P1 — Preview and public data disagree.** `LivePreview.tsx` carries `background_style`; `PUBLIC_WEDDING_FIELDS` omits it. Public rendering consequently falls back instead of honoring that persisted choice where the shared background is used. Use one typed builder-to-record-to-public mapping, and round-trip tests for every customization field.

**P2 — The richer template picker exists but is not wired into the builder.** `src/components/builder/TemplatePicker.tsx` has search, mood filters, and recommendations, but repository references show no consumer. The active builder renders the entire catalog as descriptive gradient cards, using the label “Select Wireframe Style.” Integrate the picker, show actual template thumbnails, and allow preview with the couple's content. Do not present a new picker as already available to users.

**P2 — Font choices exaggerate actual variation.** `WeddingFontProvider.tsx` intentionally maps many named font variables to three downloaded fonts or system fallbacks. This is good for transfer size but makes many options look alike and script appearance depend on the device. Offer a smaller truthful font set, or load only the selected licensed font with a reliable fallback.

**P2 — Plan/style state is inconsistent.** `isPremium` is initialized and repeatedly set to `true` in the builder, while monogram eligibility uses account access. Many premium locking branches are unreachable. This may reflect an intentional all-templates-free decision, but the dead conditions and separate vocabulary remain confusing. Document the intended free catalog, then use one feature matrix for picker, preview, save, exports, and upgrade copy.

**Mobile visual observation.** The Riviera screenshot at 375px shows its circular RSVP label broken across three lines (“RS / V / P”). Keep that label unbroken, use a clear minimum touch target, and check real long names. Classic's first screen strongly prioritizes the couple names and “scroll to explore”; test an immediately visible RSVP action and compact date/venue details. Screenshots use synthetic art, so their image quality is not representative of customer photos.

Recommended builder flow: Details → Choose design → Preview and publish, with story, gifts, entourage, monogram, gallery, and fine styling available as optional sections. Keep advanced controls accessible, but avoid requiring couples to traverse ten steps to reach the final save button. Rename internal language such as “Wireframe” and “Nicepage-inspired” into plain user-facing design descriptions.

## RSVP, guests, planner, and wedding-day operations

**P1 — Imported guests can be blocked from responding.** The public RSVP endpoint looks for any row with the same wedding and case-insensitive guest name and returns “already RSVP'd.” Planner guest creation/import writes pending entries to the same `rsvps` table. A pre-added guest therefore hits the duplicate branch even before submitting a response. Two unrelated people with the same name also collide.

Fix: separate an invited person/household's identity from its response; send opaque guest links or verify an invitation match; update the existing pending invitation. Keep an optional open-RSVP mode. Never use a display name as identity. Add idempotency: production has a unique `submission_key` index, but the current public insert does not set that field, so concurrent retries can still create duplicates.

**P1 — RSVP constraints are incomplete at the server.** The endpoint selects `rsvp_deadline` but does not enforce it. It derives `plus_one_allowed` from guest-provided numbers/names and permits up to 50 guests through validation, instead of honoring a couple-defined invitation allowance. The schema accepts “Maybe,” but the handler maps every non-Yes response to `declined`.

Fix: enforce deadline in the wedding's timezone, allowed party size, event eligibility, and response-state semantics server-side. Provide secure “change my RSVP” links rather than requiring the couple to handle every correction. Test deadline boundaries, same-name guests, imported guests, double submits, children, plus-ones, and event-specific attendance.

**P2 — Multi-event RSVP is only partially connected.** The response schema, public renderer, and live preview support events, but `BuilderForm.tsx` has no `rsvpEvents`/`rsvp_events` field wiring or persisted event configuration. Complete create/edit/save/load before promoting this as a usable builder feature.

**P1 — Budget remaining can double-count one expense.** `dashboard/[id]/planner/page.tsx:1663–1670` adds all estimates to paid vendor amounts. A 50,000 venue estimate and a 50,000 paid venue reduce remaining budget by 100,000. Unpaid contracts/deposits also need explicit semantics.

Fix: connect budget lines to vendor contracts and payments; display estimated total, contracted total, paid, outstanding, and forecast remaining separately. Exclude duplicate representations of the same commitment. Test partial payments, cancelled contracts, food linked to vendors, negative amounts, and currency behavior.

**P2 — Planner update validation is uneven.** `api/planner/items/route.ts:189` uses a task allowlist but otherwise copies arbitrary input keys except `id`/`wedding_id`. Use a per-item Zod schema with allowed columns, sensible numeric limits, and validation that linked vendor/task IDs belong to the same wedding. Current ownership checks are useful but do not replace field validation.

**Wedding-day strengths and remaining verification.** Check-in has authorization and duplicate-scan handling; photo uploads use signed upload preparation and database completion; seat lookup defaults toward code-based access. These are valuable foundations. Verify two scanners racing, seating capacity/party sizes, coordinator permissions, large guest lists, low connectivity, interrupted photo upload, moderation visibility, and expired photo access. The generic PWA fallback does not establish that offline check-in works.

**Entitlements differ by route.** Domains check only `wedding.is_premium`, while planner access accepts Account Pro too. Monogram export explicitly requires Account Pro. Publish a precise Account Pro versus per-wedding Planner Pro matrix and enforce it centrally; otherwise users can pay and still encounter unexplained locks. Review refunds/disputes too: the Stripe webhook currently fulfills completed checkouts but has no refund/dispute entitlement reconciliation. Card-only checkout means absent async-success handling is not currently an active payment-method defect.

## Architecture and operations

The monolith is a reasonable architecture for the current scale. Keep Next.js + Supabase; split responsibilities rather than introduce microservices.

- Largest app modules: builder 3,115 lines; planner page 2,494; seating builder 1,880; wedding dashboard 1,722; account dashboard 1,086. Extract feature modules and hooks with clear owners for domain logic, schemas, persistence, and display.
- Create typed models for WeddingDraft, PublicWedding, GuestInvitation, GuestResponse, BudgetLine, Payment, and Entitlement. Generate database types. Extensive `any` and mixed JSON/string arrays make save/preview drift easy.
- Make the save endpoint responsible for authorization, field validation, plan rules, version/conflict checks, and cache invalidation. The current browser upsert followed by an unawaited cache-invalidation request can report success while a public page is stale. The Redis layer caches up to ten minutes; Next adds another cache layer.
- Stop silently dropping saved fields on schema errors. The builder retries after removing missing columns, and planner loaders can turn missing schema into empty arrays. Surface “feature unavailable” and run a deployment schema check instead of presenting missing data as a successful empty state.
- `supabase/MIGRATIONS.md` declares ordered migrations authoritative, but README still tells users to execute a root recovery SQL file. Resolve that contradiction and provide a verified baseline plus reproducible staging reset. Do not rerun historical production recovery files as a deployment strategy.
- Production advisor: 35 unindexed foreign keys, 75 auth-in-RLS initialization-plan findings, and 115 overlapping-policy findings. Prioritize hot wedding/guest/planner paths with measured query plans. Do not remove the 54 flagged unused indexes solely on this snapshot. [Index guidance](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys), [RLS performance guidance](https://supabase.com/docs/guides/database/database-linter?lint=0003_auth_rls_initplan).
- Planner loading fetches every major collection and repeatedly calculates counts. Load by active tab, paginate guests/events, and use bounded aggregate queries. Current small row counts do not justify a claim of measured production slowness.
- `trackWeddingEvent` inserts directly into Supabase and ignores the returned insert error; it bypasses the rate-limited analytics API. Use one ingestion path and monitor failures. Existing analytics focus on guest activity; add product activation events without collecting guest names/emails in event metadata.
- Email quota checks/logging and sends should use reservations plus idempotent delivery jobs. Test duplicate requests, partial delivery, retries, and provider failure. Inspect actual delivery rates before claiming emails are reliable.
- Keep auth, payments, guest data, and drafts out of shared offline caches. Review service-worker account changes and cache clearing. Test accessibility with keyboard navigation, focus management, reduced motion, contrast, and screen readers; overflow tests alone are insufficient.

## Growth improvements, prioritized as experiments

Joy and Zola already advertise free websites, guest lists, and RSVP. A longer generic feature list is therefore a weak differentiator. QuickWeds can test a clearer promise around a beautiful invitation plus reliable wedding-day coordination. [Joy](https://withjoy.com/pricing/), [Zola guest management](https://www.zola.com/wedding-planning/guests).

| Priority | Experiment | Why it fits this app | Measure |
|---|---|---|---|
| 1 | Three-step first publish, recoverable draft, real preview | Makes the existing investment easier to complete | New-couple cohort reaching a valid shared site within 24h; median time to publish |
| 2 | Post-publish checklist: share link, import guests, test RSVP, invite partner | Connects the existing tools to the next meaningful action | First genuine guest response within 7 days; import-to-response failures |
| 3 | Coordinator workspace and reusable wedding setup | Coordinators can bring repeat weddings; couples usually cannot | Active coordinator partners, weddings per partner, referred activations |
| 4 | Shareable QR kit and photo album with a subtle “Create yours” link | Existing invitations and guest photos can introduce the product | Attributed guest-to-couple signup and first publish, not just clicks |
| 5 | Localized guest journey and messaging | Entourage, sponsor attire, PHP support suggest a Filipino-wedding niche worth validating | Completed guest RSVPs by language/device; interviews with target couples |
| 6 | Transparent upgrade comparison at relevant usage points | Resolve Account Pro versus wedding Pro confusion | Checkout completion, paid feature access failures, support requests |
| 7 | Curated supplier/coordinator partnerships in one region | Builds on the supplier directory without an empty broad marketplace | Qualified referrals and successful bookings; supplier retention |

For localization, validate English/Filipino demand first; support share links appropriate to the audience and household invites. Do not assume demand for every language or add paid SMS infrastructure before seeing usage.

Keep guest responses free of account-creation friction. Let premium value come from coordination, automation, controlled customization, and support. Any price or unlimited-use promise should be checked against email/storage/support cost per wedding; this audit did not evaluate unit economics.

Instrument: signup_completed, draft_started, template_selected, draft_saved, publish_succeeded, invitation_shared, first_guest_response, guest_import_completed, coordinator_invited, checkout_started, purchase_verified. Segment couple/supplier/coordinator, acquisition source, device, and signup cohort; exclude test/admin traffic. Treat first guest response as a stronger activation signal than opening the dashboard.

## Suggested delivery order

1. **First:** close production private-data exposure and entitlement writes; add role/column tests and verify live grants.
2. **Next:** repair media persistence, imported-guest RSVP, server RSVP rules, duplicate FAQ, background parity, and budget calculations. Add regression tests to these exact flows.
3. **Then:** draft autosave, three-step onboarding, real template discovery, consistent feature entitlements, publish-to-first-RSVP instrumentation.
4. **After reliability improves:** pilot with a small group of coordinators and couples, watch completion difficulties, and compare activation cohorts before increasing paid acquisition.

Release acceptance should include an authenticated staging flow: create → save draft → refresh → resume → upload/edit photos → publish → import guest → guest RSVP → seat assignment → two-device check-in → photo upload → paid entitlement access. Include anonymous/unrelated-user denials, network failure, retry, and deletion/cache checks. Keep fixture-based template checks, but do not mistake them for full application coverage.
